## 1. Зачем BGP вообще нужен

**BGP (Border Gateway Protocol)** — протокол маршрутизации, который управляет обменом маршрутной информацией между **автономными системами (AS, Autonomous System)**. Это единственный протокол, на котором держится маршрутизация в интернете и в крупных корпоративных/операторских сетях.

Ключевое отличие BGP от IGP-протоколов (OSPF, IS-IS, EIGRP):

| Параметр | IGP (OSPF, IS-IS) | BGP |
|---|---|---|
| Область применения | Внутри одной AS | Между AS и внутри AS |
| Метрика выбора маршрута | Математическая (стоимость линка) | Политика (набор атрибутов, "policy-based") |
| Масштаб | Сотни-тысячи маршрутов | Сотни тысяч — миллионы маршрутов (full table ~900k+) |
| Скорость сходимости | Быстрая | Медленнее, но стабильнее при больших масштабах |
| Транспорт | Свой (multicast/broadcast) | TCP порт 179 (надёжный, ориентированный на соединение) |

**Важно понимать с первого дня:** BGP — это протокол **политик**, а не протокол "кратчайшего пути". Он выбирает маршрут не по метрике расстояния, а по набору атрибутов, которые администратор может настраивать под бизнес-задачи (например, "предпочитать транк через Ростов, а не через Краснодар").

## 2. Базовые понятия

- **AS (Autonomous System)** — сеть или группа сетей под единым административным управлением, с единой политикой маршрутизации. Идентифицируется номером **ASN** (Autonomous System Number). Бывают:
  - **Public ASN** (1–64495, 131072–4199999999) — уникальные в интернете, регистрируются в RIR (RIPE, ARIN и т.д.);
  - **Private ASN** (64512–65534 для 16-бит, есть расширенный диапазон для 32-бит) — используются внутри частных сетей, не видны в глобальном интернете.

- **BGP Speaker** — маршрутизатор, на котором запущен процесс BGP.

- **BGP Peer / Neighbor** — сосед, с которым установлена BGP-сессия.

- **NLRI (Network Layer Reachability Information)** — собственно префикс сети (например, `10.10.0.0/24`), который анонсируется через BGP.

- **RIB (Routing Information Base)** — таблица маршрутов. В контексте BGP различают:
  - **Adj-RIB-In** — маршруты, полученные от соседа до применения входящей политики;
  - **Loc-RIB** — локальная таблица после выбора лучшего маршрута;
  - **Adj-RIB-Out** — маршруты, которые будут отправлены соседу после применения исходящей политики.

- **BGP Table (RIB) vs IP Routing Table (FIB)** — не путать: в BGP таблице может быть несколько маршрутов до одного префикса (от разных соседей), в таблицу маршрутизации (FIB) попадает только лучший.

## 3. eBGP vs iBGP — принципиальная разница

### eBGP (External BGP)
Сессия между маршрутизаторами, принадлежащими **разным AS**.

- По умолчанию TTL = 1 (соседи должны быть напрямую связаны, если не используется `ebgp-multihop`);
- AS_PATH при получении маршрута **дополняется номером AS** передающей стороны — это и есть механизм защиты от петель на уровне AS;
- Типичный пример: граница вашей сети (AS вашего оператора) — граница AS другого оператора/аплинка.

### iBGP (Internal BGP)
Сессия между маршрутизаторами **внутри одной AS**.

- Используется, когда внутри одной AS несколько пограничных (edge/border) маршрутизаторов должны видеть одну и ту же внешнюю маршрутную информацию;
- AS_PATH **не изменяется** при передаче внутри AS (номер AS не добавляется) — иначе протокол не смог бы отличить "внутренний" маршрут от "внешнего", и это ломало бы логику Loop Prevention;
- Именно из-за того, что AS_PATH не растёт внутри AS, для предотвращения петель придумано отдельное правило — **iBGP Split-Horizon** (см. раздел 4);
- TTL обычно не ограничен (соседи могут быть не напрямую связаны, трафик BGP-сессии идёт через IGP);
- Next-Hop по умолчанию **не меняется** при передаче через iBGP (в отличие от eBGP, где Next-Hop обычно меняется на адрес пограничного маршрутизатора) — это частый источник проблем "маршрут в таблице есть, а пакеты не идут" (см. раздел 10).

**Аналогия для понимания:** представь AS как отдельную компанию. eBGP — это переговоры между разными компаниями (кто, что и на каких условиях готов "провозить" через себя). iBGP — это внутренняя служебная переписка внутри одной компании, чтобы все филиалы (пограничные маршрутизаторы) знали, что уже "напереговаривали" с внешним миром на разных границах.

## 4. Правило Split-Horizon для iBGP и способы его обхода

Это **критически важное правило**, которое ломает голову большинству новичков.

### Правило
> Маршрутизатор, получивший маршрут через **iBGP**, **не может** переанонсировать его другому **iBGP**-соседу.

Маршрут можно передать дальше только если он получен через **eBGP**, либо является локально сгенерированным (network-команда, редистрибуция).

**Зачем это правило:** поскольку AS_PATH внутри AS не растёт, единственный способ избежать бесконечных петель при пересылке маршрутов между iBGP-соседями — жёстко запретить ретрансляцию "iBGP → iBGP".

### Следствие
Из правила напрямую вытекает требование: **все iBGP-маршрутизаторы внутри AS должны быть связаны сессиями BGP друг с другом напрямую** — это называется **iBGP Full Mesh**.

Для N маршрутизаторов внутри AS понадобится:
```
Количество сессий = N × (N-1) / 2
```
При N=10 это уже 45 сессий на каждый роутер держать конфигурацию — не масштабируется на больших сетях (а сеть с присутствием в Крыму, Херсонской, Запорожской, Донецкой областях, Ростове и Краснодаре — это уже десятки узлов).

### Способы обхода Full Mesh

**1. Route Reflector (RR) — маршрутный отражатель**
- Один или несколько маршрутизаторов назначаются "отражателями". Остальные (route reflector clients) устанавливают сессию только с RR, а не друг с другом.
- RR **разрешено** переотражать маршрут, полученный от одного iBGP-клиента, другим iBGP-клиентам — это исключение из правила Split-Horizon, специально введённое для RR.
- Термины: **RR (Route Reflector)**, **Client (клиент RR)**, **Non-client (обычный iBGP-сосед RR)**.
- Для защиты от петель при использовании RR вводятся атрибуты **ORIGINATOR_ID** и **CLUSTER_LIST** (см. раздел 5).
- На практике: обычно RR ставят на узлы ядра сети (core), а пограничные/агрегационные узлы регионов (Крым, Ростов, Краснодар и т.д.) — клиенты.

**2. BGP Confederation**
- AS делится на суб-AS (sub-AS) с приватными номерами, внутри каждой суб-AS — full mesh, между суб-AS — eBGP-подобные сессии (но AS_PATH обрабатывается по особым confederation-правилам).
- Используется реже RR, обычно в очень крупных сетях/при слияниях сетей разных операторов под одним ASN.

**На практике в большинстве операторских сетей используют Route Reflector — это проще в администрировании и более распространено, в т.ч. на оборудовании Huawei.**

## 5. Атрибуты маршрутов BGP

Атрибуты — это "паспорт" маршрута, на основе которого принимается решение о выборе лучшего пути. Делятся на 4 категории:

| Категория | Описание | Примеры |
|---|---|---|
| Well-known mandatory | Обязателен, должен присутствовать во всех обновлениях | AS_PATH, NEXT_HOP, ORIGIN |
| Well-known discretionary | Известен всем, но необязателен | LOCAL_PREF, ATOMIC_AGGREGATE |
| Optional transitive | Может не пониматься, но передаётся дальше | COMMUNITY, AGGREGATOR |
| Optional non-transitive | Может не пониматься, если непонятен — отбрасывается | MED, ORIGINATOR_ID, CLUSTER_LIST |

### Ключевые атрибуты подробно

**AS_PATH**
Список номеров AS, через которые прошёл маршрут. Используется как основной механизм Loop Prevention для eBGP: если маршрутизатор видит в AS_PATH собственный номер AS — маршрут отбрасывается. Чем короче AS_PATH — тем маршрут обычно предпочтительнее (но это не единственный и не первый критерий выбора).

**NEXT_HOP**
IP-адрес следующего хопа для достижения префикса.
- В eBGP при анонсировании соседу NEXT_HOP обычно меняется на адрес анонсирующего маршрутизатора;
- В iBGP NEXT_HOP по умолчанию **сохраняется неизменным** — это значит, что внутренний iBGP-роутер должен иметь IGP-маршрут (через OSPF/IS-IS) до этого NEXT_HOP, иначе маршрут будет считаться **невалидным (inactive)** и не попадёт в таблицу маршрутизации, даже если BGP-сессия Established. Это одна из самых частых практических ошибок.

**LOCAL_PREF (Local Preference)**
Атрибут, передаваемый **только внутри AS (iBGP)**, не передаётся eBGP-соседям. Показывает предпочтительность выхода из AS через конкретный маршрутизатор. Чем **выше** значение — тем маршрут предпочтительнее. Классический пример: "весь трафик на определённые внешние сети предпочитаем гнать через аплинк в Ростове, а не в Краснодаре" — настраивается через LOCAL_PREF.

**MED (Multi-Exit Discriminator)**
Атрибут, которым AS сообщает соседней AS, через какую из нескольких точек стыка предпочтительнее заходить трафику. Чем **ниже** значение — тем предпочтительнее. В отличие от LOCAL_PREF, влияет на решение соседа, а не собственной AS. По умолчанию сравнивается только между маршрутами от **одной и той же соседней AS**.

**ORIGIN**
Показывает происхождение маршрута:
- `IGP` (i) — маршрут введён через команду `network`;
- `EGP` (e) — устаревший, практически не встречается;
- `Incomplete` (?) — маршрут получен через редистрибуцию из другого протокола.
Приоритет: IGP > EGP > Incomplete.

**COMMUNITY**
32-битная метка (обычно формат `AS:значение`), которая "навешивается" на маршрут для последующей фильтрации/применения политик на других узлах, без необходимости писать сложные route-map/prefix-list на каждом узле отдельно. Очень активно используется операторами связи для маркировки маршрутов (например, "маршрут из региона Крым", "маршрут от конкретного клиента", "не анонсировать дальше определённым партнёрам").

**ORIGINATOR_ID и CLUSTER_LIST** (актуальны при использовании Route Reflector)
- **ORIGINATOR_ID** — Router ID маршрутизатора, изначально введшего маршрут в iBGP. Если RR получает маршрут со своим же ORIGINATOR_ID — отбрасывает его (защита от петель);
- **CLUSTER_LIST** — список кластеров RR, через которые прошёл маршрут. Аналог AS_PATH, но для внутренней иерархии RR.

**WEIGHT** (не стандартный атрибут BGP, а проприетарная фича, локальная для маршрутизатора, самый первый критерий в выборе пути у Cisco; на Huawei есть аналог — **Preferred-Value**).

## 6. Алгоритм выбора лучшего маршрута (Best Path Selection)

Когда до одного префикса приходит несколько маршрутов от разных соседей, BGP выбирает **только один** лучший маршрут (для помещения в Loc-RIB и далее в таблицу маршрутизации). Порядок проверки (типовой, для Huawei VRP — с небольшими нюансами по сравнению с Cisco, но логика та же):

1. Маршрут должен быть **валидным** (Next-Hop достижим через IGP) — иначе сразу отбрасывается;
2. Наибольший **PreVal / Preferred-Value** (аналог Weight, локальный, не передаётся по сети);
3. Наибольший **LOCAL_PREF**;
4. Маршрут, **локально сгенерированный** (через `network`/`import`) предпочтительнее полученного извне;
5. Кратчайший **AS_PATH**;
6. Наименьший (лучший) **ORIGIN** (IGP < EGP < Incomplete);
7. Наименьший **MED** (сравнение только между маршрутами от одной соседней AS, если не включена специальная опция `compare-different-as-med`);
8. Предпочтение маршруту, полученному через **eBGP**, а не через iBGP;
9. Наименьшая метрика IGP до NEXT_HOP;
10. Для eBGP-маршрутов — старейший маршрут (дольше всего находящийся в таблице) — снижает "дребезг" (flapping);
11. Наименьший **Router ID** соседа;
12. Наименьший **Cluster List** (если есть RR);
13. Наименьший IP-адрес соседа (peer address) — как финальный tie-breaker.

**Практический вывод:** если два маршрута кажутся "одинаковыми", но выбирается почему-то не тот, что ожидался — проходи этот список сверху вниз и проверяй атрибуты через `display bgp routing-table <префикс>` — почти всегда причина находится в пунктах 2–7.

## 7. Состояния BGP-сессии (FSM)

BGP-сессия проходит через конечный автомат состояний (Finite State Machine):

```
Idle → Connect → Active → OpenSent → OpenConfirm → Established
```

| Состояние | Что происходит |
|---|---|
| **Idle** | Начальное состояние. Сессия не активна, ожидание запуска (событие Start) |
| **Connect** | Маршрутизатор пытается установить TCP-соединение (порт 179) |
| **Active** | TCP-соединение не удалось, идут повторные попытки установить его |
| **OpenSent** | TCP-соединение установлено, отправлено сообщение OPEN, ожидание OPEN от соседа |
| **OpenConfirm** | Оба OPEN-сообщения получены и приняты, ожидание KEEPALIVE |
| **Established** | ✅ Сессия полностью установлена, идёт обмен маршрутами (UPDATE) |

**Для мониторинга критично:**
- Нормальное рабочее состояние — только **Established**;
- Если сессия "застряла" в **Active** — почти всегда проблема на транспортном уровне (нет связности, блокировка TCP/179 на ACL/firewall, неверный peer-адрес);
- Частые переходы Established → Idle → Established ("flapping") — признак нестабильности линка, проблем с MTU, конфликта Router-ID, либо истечения Hold Timer из-за перегрузки CPU/линка.

**Типы сообщений BGP:**
- **OPEN** — установление сессии, обмен параметрами (версия, ASN, Hold Time, Router ID, capabilities);
- **UPDATE** — анонс/отзыв маршрутов;
- **KEEPALIVE** — поддержание сессии живой (по умолчанию каждые 60 сек, Hold Time — 180 сек, если не переопределено);
- **NOTIFICATION** — сообщение об ошибке, после которого сессия рвётся (содержит код и подкод ошибки — первое, что нужно смотреть в логах при обрыве).

## 8. Настройка BGP на оборудовании Huawei (VRP)

Базовые команды для понимания синтаксиса (VRP CLI):

### Включение процесса BGP и задание Router ID
```
system-view
bgp 65001
 router-id 10.0.0.1
```

### Настройка eBGP-соседа
```
bgp 65001
 peer 192.168.1.2 as-number 65002
 peer 192.168.1.2 description UPLINK-TO-ISP-X
```

### Настройка iBGP-соседа (тот же ASN)
```
bgp 65001
 peer 10.1.1.2 as-number 65001
 peer 10.1.1.2 description iBGP-to-CORE-RR
```

### Анонсирование сети
```
bgp 65001
 ipv4-family unicast
  network 192.168.10.0 255.255.255.0
  peer 10.1.1.2 enable
```

### Настройка Route Reflector
На RR (например, узел ядра):
```
bgp 65001
 ipv4-family unicast
  peer 10.1.1.2 reflect-client
  peer 10.1.1.3 reflect-client
```

### Настройка LOCAL_PREF через route-policy
```
route-policy PREFER_ROSTOV permit node 10
 if-match ip-prefix PL_ROSTOV
 apply local-preference 200
route-policy PREFER_ROSTOV permit node 20
 apply local-preference 100
!
bgp 65001
 ipv4-family unicast
  peer 10.1.1.2 route-policy PREFER_ROSTOV import
```

### Полезные команды просмотра (must know наизусть)
```
display bgp peer                          — статус всех BGP-сессий
display bgp peer verbose                  — детально по соседям (таймеры, capabilities)
display bgp routing-table                 — вся BGP-таблица
display bgp routing-table <ip>/<mask>     — атрибуты конкретного маршрута
display bgp routing-table different-origin-as   — маршруты с разным origin AS (защита от аномалий)
display bgp network                       — локально анонсированные сети
reset bgp <peer-ip>                       — сброс сессии (осторожно! может уронить продакшн)
display bgp routing-table statistics      — статистика по количеству маршрутов
```

> ⚠️ **Важно на первых неделях работы:** команда `reset bgp all` или `reset bgp <as-number>` может разом уронить множество сессий и вызвать значительный простой — никогда не выполнять без согласования и понимания последствий.

## 9. Мониторинг BGP в Zabbix

Что именно нужно мониторить и почему:

### 1. Состояние сессии (Session State)
- Источник данных: SNMP (`bgpPeerState` — OID `1.3.6.1.2.1.15.3.1.2`) либо через Huawei-специфичный MIB (`hwBgpPeerState`), либо через NETCONF/скрипт-парсер вывода `display bgp peer`.
- Триггер: alert при переходе из **Established** в любое другое состояние дольше N секунд (защита от ложных срабатываний на кратковременный flap).

### 2. Количество принятых/анонсированных префиксов
- Резкое падение числа префиксов от соседа — признак проблемы на его стороне (например, потеря части клиентских маршрутов);
- Резкий рост — признак утечки маршрутов (route leak) — потенциально опасная ситуация (например, случайная переанонсация full-table).
- Полезно ставить **min/max триггеры** ("нормальный диапазон" количества префиксов от конкретного соседа) — под каждый линк/регион своя норма.

### 3. Flapping (нестабильность сессии)
- Считать количество переходов Established↔Idle за период (например, за час);
- Более 2–3 flap за короткий период — сигнал для эскалации, вероятна проблема физического линка или перегрузка.

### 4. Uptime сессии
- Метрика `bgpPeerFsmEstablishedTime` — как давно сессия в Established. Полезно для истории инцидентов и SLA-отчётности.

### 5. Использование CPU/памяти процесса BGP на узле
- Особенно критично на узлах с Route Reflector — при большом количестве клиентов и полной таблице интернет-маршрутов (900k+ префиксов) нагрузка может быть существенной.

### Практическая схема мониторинга
```
Zabbix Server
   │
   ├── SNMP polling (bgpPeerState, bgpPeerFsmEstablishedTime, bgpPeerInUpdates...)
   │      → узлы Huawei (NE/CE серии) как правило поддерживают собственный BGP MIB
   │
   ├── Скрипт-обвязка (Zabbix Agent / внешние скрипты)
   │      → парсинг display bgp peer verbose при необходимости более детальных данных,
   │        которых нет в стандартном MIB
   │
   └── Триггеры + Эскалация
          → Established→Idle (severity: High)
          → Резкое изменение числа префиксов (severity: Warning/High в зависимости от %)
          → Flapping > N раз/час (severity: High)
```

### Практический совет
Заведи для себя (и для команды) **baseline** — эталонное количество BGP-сессий и эталонное число префиксов по каждому узлу/региону (Крым, Херсонская, Запорожская, Донецкая области, Ростов, Краснодар) в нормальном рабочем состоянии. Без этой базы любые триггеры "резкое изменение" настраивать бессмысленно — не с чем сравнивать.

## 10. Типичные проблемы и диагностика

| Симптом | Вероятная причина | Куда смотреть |
|---|---|---|
| Сессия зависла в Active | Нет IP-связности до соседа, ACL блокирует TCP/179, неверный peer address | `ping`, `display current-configuration \| include acl`, проверка маршрута до peer |
| Сессия зависла в OpenSent/OpenConfirm | Не совпадает AS-номер, Router-ID конфликт, несовпадение capabilities | `display bgp peer verbose`, логи NOTIFICATION |
| Established, но трафик не идёт | Классическая проблема iBGP: Next-Hop недостижим через IGP (правило из раздела 3) | `display bgp routing-table <prefix>` → смотреть валиден ли маршрут (Valid/Best), проверить `display ip routing-table` для Next-Hop |
| Маршрут получен, но не выбран Best | Атрибуты хуже, чем у конкурирующего маршрута | Пройти по чек-листу алгоритма Best Path (раздел 6) |
| Постоянный flapping сессии | Нестабильный линк, MTU mismatch, перегрузка CPU/памяти, истечение Hold Timer | Статистика интерфейса (ошибки/drops), `display bgp peer verbose` → причина последнего сброса |
| Внезапный рост числа маршрутов от соседа | Route leak / ошибочная переанонсация full table | Немедленно проверить route-policy/filter на входящей стороне, при необходимости — временный `peer ... route-limit` |
| iBGP-маршрут не передаётся дальше другому iBGP-соседу | Забыли, что это правило (Split-Horizon), либо не настроен Route Reflector там, где он нужен | Проверить, является ли узел RR, клиентом ли является получатель |

## 11. Мини-глоссарий

- **AS** — автономная система, зона единого управления маршрутизацией.
- **ASN** — номер автономной системы.
- **Peer / Neighbor** — сосед по BGP-сессии.
- **NLRI** — сетевой префикс, анонсируемый в BGP.
- **RIB** — таблица маршрутов BGP (In/Loc/Out).
- **FIB** — итоговая таблица маршрутизации (Forwarding).
- **Route Reflector (RR)** — маршрутизатор, которому разрешено переотражать iBGP-маршруты другим iBGP-клиентам.
- **Full Mesh** — топология, при которой все iBGP-роутеры соединены друг с другом напрямую.
- **MED** — атрибут для влияния на выбор точки входа трафика соседней AS.
- **LOCAL_PREF** — атрибут для влияния на выбор точки выхода трафика из своей AS.
- **Flapping** — частое переключение состояния сессии/маршрута (нестабильность).
- **Route Leak** — утечка маршрутов, ошибочная переанонсация маршрутов не в ту сторону.

## 12. Практическое задание для закрепления

Чтобы материал закрепился — выполни (в лабораторной среде, например eNSP от Huawei, или на тестовом стенде, не в продакшне):

1. Подними 3 виртуальных маршрутизатора Huawei в одной AS (например AS 65001) и настрой между ними **iBGP Full Mesh**.
2. Убедись, что маршрут, полученный одним роутером через iBGP, **не передаётся** дальше третьему (проверь правило Split-Horizon на практике командой `display bgp routing-table`).
3. Добавь четвёртый роутер как **Route Reflector**, перестрой топологию в "звезду" через RR вместо full mesh, и убедись, что теперь маршрут доходит до всех.
4. Подключи пятый роутер как eBGP-сосед (другой AS, например 65002), анонсируй с него тестовую сеть, проследи, как меняется AS_PATH и Next-Hop при прохождении через границу AS.
5. Через `route-policy` настрой разное значение LOCAL_PREF для разных входных точек и убедись, что маршрут выбора пути меняется предсказуемо (сверяясь с алгоритмом из раздела 6).

После выполнения — сформулируй (себе, в конспект) своими словами: **почему нельзя просто взять и передать iBGP-маршрут другому iBGP-соседу без Route Reflector**. Если объяснение получится связным и без "подглядывания" в методичку — тема усвоена.
